# RackPulse MVP 设计（待用户审阅）

## 目标与范围

为 GPU 数据中心运维人员每天自动生成上一自然日中文日报，替代人工查询和统计。交付 Thanos 只读采集、32 个 GB200 机柜统计、持续异常检测、飞书通知、历史存储、手动重跑以及 Docker Compose 部署。第一版不建设 Web 界面、多集群、AI 总结和其他通知渠道；通过接口预留扩展。

验收以用户提供的 V1.0 需求第 13 节为准。真实连接和飞书投递需现场地址、鉴权及凭据，未配置时不得声称验收成功。演示数据与真实报告明确区分。

## 方案选择

已选择：按机柜显式配置 PSU 品牌，分别查询厂商指标，在应用层归一化。每机柜只有一种品牌、预期 48 路。自动发现只辅助配置，不作为缺失时的品牌推断。

另一方案是同时查询两种厂商后自动判断归属，初期配置少，但全量缺失时不能确定品牌，不作为正式统计方案。

提议的持久化方案：MVP 即使用 PostgreSQL，而非先用本地文件再迁移，以支持重跑、断点恢复、任务互斥及通知记录。Python 3.12、FastAPI、httpx、APScheduler、SQLAlchemy，YAML 配置和环境变量；不引入 Pandas 作为必要依赖。

## 配置与设备身份

- 配置预置 GB200-1-1 至 GB200-1-16、GB200-2-1 至 GB200-2-16，分别预期 72 GPU、48 PSU。
- 每机柜配置 GPU host 正则及 psu_vendor（liteon/delta）。未知映射标记未配置；启动检查列出所有缺项，不编造映射或品牌。正式全量任务要求配置齐全。
- 已知 GB200-2-7 的 GPU host 映射为 GB200-POD2-E15-.*。
- GPU 指标 gpu_utilization_percent（0–100）与 gpu_power_watts（W），身份使用 host + gpu_id，并保留 uuid/sn 作诊断信息。
- PSU 指标 liteon_psu_input_power_watts 或 delta_psu_input_power_watts（W），使用 rack + host + psu_id 标识物理槽位，保留厂商和 sn。编号起点不参与数量判断。
- 同机柜出现另一厂商数据报配置/数据冲突，不相加。忽略抓取副本标签进行身份归一化，冲突值不得任意累加；重复且不一致的数据标记无效并报告。
- 查询启用 Thanos 去重；不接受无提示的部分响应。host 匹配多个机柜时拒绝该配置。

## 时间与采集

统一 Asia/Shanghai；08:00 执行上一日任务。统计窗口为 [当日00:00, 次日00:00)，默认 60 秒，共 1440 个桶。query_range 终点为次日00:00减60秒，避免闭区间重复。

按机柜、指标和小时分块采集，可配置超时、并发上限、限流、重试与退避。仅瞬时失败重试；永久鉴权或语法错误明确失败。显式配置原始分辨率，检查 API warnings。采样必须检查原始样本新鲜度（默认最大120秒，可配置），避免 Prometheus lookback 将旧值当作持续采集。

采集块写临时检查点，记录窗口、配置指纹及成功状态；同配置同窗口恢复成功块。报告提交后清理临时分钟数据，失败检查点保留期限可配置。数据库仅长期保留日汇总和事件。

## 统计口径

按机柜、每分钟对有效物理设备去重。NaN/Inf、负功率及范围外利用率视为无效；零值有效。超出预期数量报告身份/配置异常，覆盖率不允许超过100%。

分别展示日内出现设备数量、每分钟有效数量及完整率；采样完整率=有效设备分钟数/(预期设备数×1440)。单次出现不表示全天完整。

利用率均值基于有效设备分钟，最大值取有效单卡峰值。高低负载比例以有效设备分钟为分母，同时报告缺失比例。机柜负载持续时间基于该分钟有效 GPU 的均值，并附覆盖率；缺失分钟打断连续区间。单卡高低负载时长另行汇总，避免混淆 GPU 小时与机柜小时。

每分钟功率来源：48路完整有效PSU为完整PSU；1–47路为部分PSU实测和；0路且有GPU功率为GPU代理和；两者均无为缺失。分别保存来源、设备数、平均值、峰值和覆盖分钟数。GPU代理不表示机柜总功率。

能耗按有效分钟功率×1/60小时积分，W转kWh；缺失不填零、不外推全天。来源变化分段计算，分别显示可观测能耗及覆盖率，不把混合来源包装成完整全天能耗。全局功率也分来源汇总。

昨日比较只对同来源、设备集合及覆盖条件可比的数据生成；否则标记不可比。MVP提供前日比较，7/30日趋势接口留待后续。

## 异常与日报

规则可配置：GPU/PSU数量少于预期为Warning；连续10分钟全无有效监控为Critical；GPU均值低于10%或达到80%持续60分钟为Info。GPU/PSU设备缺失以分钟区间记录，日内出现数量仅作辅助。高负载不是故障。

功率规则提议使用此前7日完整PSU分钟数据的日均值中位数作为基线，至少3个有效日且每日完整覆盖率≥95%，要求当前分钟48路完整且设备集合一致；偏离超过30%为Warning。无合格基线标记未评估；部分PSU和GPU代理不参与。首次运行不虚构历史基线。

事件记录机柜、设备（机柜事件可为空）、类型、等级、开始、恢复、持续时间、指标值及规则版本。日报末仍持续的事件标为未恢复，窗口末端不是恢复时间；跨日通过相邻检查点连续性关联。原因与操作使用规则建议，明确为可能性。

中文日报包含整体摘要、GPU负载、分来源功率能耗、异常区间、采集完整性、昨日对比及人工关注项。Info不计入故障机柜；Warning/Critical计异常机柜；无法评估机柜单列，不计正常。每项可追溯到统计窗口、配置与规则版本。

## 存储、任务及接口

PostgreSQL保存机柜配置快照、每日汇总、事件、日报版本、执行记录、采集检查点和通知记录。数据库迁移随部署提供。

日报唯一键为统计日期与集群（MVP默认单集群）；重跑生成内部修订版本并原子切换当前日报，不生成多个当前日报。同日期任务使用数据库锁，调度器仅单实例启用。失败不覆盖最后成功版本，部分采集报告明确标为不完整。

提供健康/就绪检查、按日期生成、任务状态、日报查询、测试通知、重新推送接口；日期输入按北京时间解释。变更接口需要环境变量提供的API token，默认不公开端口访问。长任务返回任务ID。没有历史数据时返回缺失状态。

## 飞书通知与幂等边界

通知适配器以结构化日报为输入，MVP实现飞书；长度超限用摘要和确定性分段。测试消息明确标记测试。Webhook与签名密钥来自环境变量，不进入报告、URL日志或异常文本。

数据库通知唯一约束为日期、渠道、内容哈希；相同内容重跑不自动重复发送。修改后的日报默认只更新存储，重新发送由手动接口显式触发并留审计记录。

明确可重试的限流或失败使用退避；检查HTTP及飞书业务码。发送后超时可能已送达，标记unknown，不盲目重发，允许人工核实后强制发送。外部Webhook没有接收端幂等保证，因此不能承诺端到端恰好一次。

## 部署、安全与验证

Compose包含应用与PostgreSQL，非root应用容器、持久卷、健康检查、JSON日志；日志统一脱敏。Thanos仅调用只读查询，所有请求有超时；凭据使用未入库的环境文件，提供无真实密钥的示例。

验证覆盖时间边界、双品牌及身份去重、缺采和陈旧采样、功率来源切换、持续与跨日异常、基线不足、任务恢复、并发重跑、通知不确定状态和凭据脱敏。集成测试使用固定Thanos/飞书响应，另提供现场只读验证命令。

## 待部署补齐与实现者裁量

待提供Thanos地址及鉴权、32柜GPU映射与PSU品牌、飞书Webhook和可选签名密钥；均通过配置提供，不阻碍用夹具开发验证。

上述120秒新鲜度、基线门槛、单实例调度、API鉴权和修订默认不自动通知为本设计提议，尚非用户逐项确认。实现者可决定模块目录、迁移工具、重试次数、日志库和报告排版，不能改变指标语义或用模拟数据冒充真实验收。

## 审阅补充

审阅发现的两处依赖已明确：每日另行持久化规则日末状态，不随采集检查点清理；历史重跑后重新关联次日事件，若次日摘要受影响则标记待重算，不静默改动已发送报告。正式采集增加另一品牌的轻量存在性检查，用于识别品牌冲突，返回数据不纳入功率求和。审阅后无阻碍实施计划的重要未决问题。
